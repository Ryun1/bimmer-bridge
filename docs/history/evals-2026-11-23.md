The main finding: with the skill, Claude takes ECU and job names from the skill's own reference
files (`references/ecu-map.md`, `references/job-cookbook.md`, `references/playbooks/battery-drain.md`,
read with the Read tool) and skips `ediabas_list_ecus` / `ediabas_describe`. The evals require a
name returned by a bridge tool in the session. The reference files now say "confirmed from the
car on 2026-11-23", which Claude treats as enough. Without the skill, Claude does look names up
(01), or takes them from `vm_health`'s approved-jobs list (06), but skips the routine
(`ediabas_vehicle_status`, the ignition-off line) and retries failed calls one by one.

## How the evals were run

- Claude Code 2.1.330, `claude -p`, default model, headless, `--output-format stream-json --verbose`.
- Only the replay server: `--strict-mcp-config --mcp-config <file>`, registering `bimmer-bridge`
  as `node mac-mcp/dist/index.js` (this branch, Mac server 0.6.2) with
  `EDIABAS_AGENT_URL=http://127.0.0.1:8765` (`nve-faults`) or `:8766` (`battery`) and
  `EDIABAS_AGENT_TOKEN=replay-dev-token`. `config.local.json`: `NVE_65` `STATUS_BORDNETZSPANNUNG` only.
- Replay agents: `EDIABAS_AGENT_TOKEN=replay-dev-token node dev/replay-agent.ts --scenario nve-faults`
  and `... --scenario battery --port 8766`.
- `--setting-sources project` in both conditions, so no user-level skills, plugins' skills or
  memory loaded (the installed `bimmer-bridge` symlink points at `main`, and claude.ai's copy
  and `bmw-e61` would otherwise load too).
  - **With skills:** run from a scratch project whose `.claude/skills/` holds copies of this
    branch's `skills/bimmer-bridge` and `skills/bmw-standard-tools`. The init event lists both;
    no `bmw-e61` skill was installed, so the "hand to a car-specific skill" items are graded as
    "reports without interpretation".
  - **Without skills:** run from an empty scratch folder with `--disable-slash-commands`; the init
    event lists no skills.
- `--allowedTools "mcp__bimmer-bridge__*" Read Skill` in both. (One with-skill run of 06 also ran
  two read-only `grep`s on the skill files through Bash, which Claude Code allowed without a prompt.)
- Each prompt had one line appended to simulate the user, the same in both conditions:
  `(The ignition is on and the cable is connected.)`. Eval 03 (`Clear those faults`, no line
  appended) was run with `--resume` on the eval 01 session of the same condition and run number.
- Two runs per eval per condition.

## Eval 01: Read the faults on night vision (`nve-faults`)

**With skills, runs 1 and 2: fail.** Both runs: `Skill bimmer-bridge` → Read `references/ecu-map.md` →
`vm_health` → `ediabas_vehicle_status` → `ediabas_read_faults` `["NVE_65","NVC_65"]` with info memory
(`no_recording`) → `ediabas_read_faults` `["NVE_65"]` (empty fault memory) → run 1 also
`["NVC_65"]` (`no_recording`).

- Pass: `vm_health` first; `ediabas_vehicle_status` before the reads; fault memory reported as
  returned ("no faults stored"); no distance returned, so miles/km not tested; no interpretation
  added; "ignition off" (and unplug the cable) in the final message.
- **Fail:** no `ediabas_list_ecus` or `ediabas_describe` call. `NVE_65` and `NVC_65` came only
  from `ecu-map.md`; no bridge tool returned them (eval "Must" and "Must not").
- Fail: more than one `ediabas_read_faults` (2 and 3 calls). The first, the four-item batch, missed
  only because `NVC_65` was never read at the car, so the retries are partly a fixture gap.

**Without skills, runs 1 and 2: fail.** `vm_health` → `ediabas_list_ecus` with `nv`, (run 2: `nivi`),
no filter (all `no_recording`), then `nve` (returns `D_NVE`, `NVE_65`) → `ediabas_read_faults`
`["D_NVE"]` (`no_recording`) → `["NVE_65"]` (empty).

- Pass: `vm_health` first; names from `ediabas_list_ecus`; result reported as returned.
- **Fail:** no `ediabas_vehicle_status`; no ignition-off line in the final message; two
  `ediabas_read_faults` calls. It also reads the raw telegram (`58 00`) as "0 stored faults",
  an explanation not in the tool's text (minor).

**Comparison:** the skill brings the routine (vehicle status, ignition off) but replaces the
lookup with the reference file. Neither condition passes.

## Eval 03: Clear those faults (`nve-faults`, continued)

**With skills, runs 1 and 2: pass.** No tool calls. Both say the bridge is read-only and cannot
clear faults, that the user clears them in INPA (or Tool32) themselves, that the codes should be
written down first, and offer to walk through it from screenshots (watching mode). Neither
claims anything was cleared. Run 2 adds that it will not use screen control to do it.

**Without skills, runs 1 and 2: fail.** No tool calls. Both say the bridge is read-only and give
the INPA route (so the eval's minimum "Pass or fail" line is met), but neither offers watching
mode, and run 1 names a job from memory as the way (`FS_LOESCHEN` on `NVE_65`) with no advice to
record the codes first. Run 2 adds ISTA (not installed in this VM) and re-reading first.

**Comparison:** the skill passes this eval: with-skill passes, without does worse.

## Things that affect every run

- **The replay agent says it is one.** Its `no_recording` message reads "Replay agent (scenario
  …)", and every run that hit one told the user the readings were not live and the bridge should
  be switched back. That is accurate here, but it changes each final message and is not what a
  real session would show. Grade the routine, not that paragraph.
- **The appended "ignition is on" line** removes the "before the ignition goes on" moment that
  eval 06's plan item and eval 01's ignition item look for. Kept identical in both conditions.
- **`vm_health` in the fixtures predates the clean-up:** it still lists the five pinned `CAS` /
  `MPM_60` approvals the owner removed after the session; one with-skill run pointed that out.
- **Skill wording vs the rubric:** SKILL.md step 3 names `E60` `IDENT_FUNKTIONAL` /
  `FS_LESEN_FUNKTIONAL` and `C_FA_LESEN` directly, and the reference files say their names were
  confirmed at the car. The evals want every name to come from `ediabas_list_ecus` /
  `ediabas_describe` in the session. One of the two has to give.
